## Problema comprovado

O caminho público instalado ainda não seleciona uma composição operacional. O probe isolado abaixo
inicializou o scaffold real e executou o comando público sem monkeypatch:

```text
init_exit=0
run_exit=1
Error: agent node executor backend is unavailable
```

O teste baseline correspondente passou `1 passed in 1.20s` porque
`tests/unit/test_cli_runtime.py::test_cli_run_status_inspect_lifecycle` exige justamente essa falha.
A causa direta está em `src/ai_engineering_harness/cli/main.py`: `_lifecycle_service()` injeta
`NodeExecutorRegistry()` vazio. A prova F7.1 em `tests/e2e/test_external_repository_product.py`
atravessa o produto somente após construir `InstalledWheelAgentBackend`, provider, tool router,
worktree, promotion e rollback dentro de uma fixture. Logo, a wheel contém as primitivas, mas a
factory pública não as compõe.

A auditoria revelou uma segunda lacuna estrutural vinculada: o grafo default `new-feature` declara
roles e tools conceituais que não correspondem diretamente aos adapters operacionais registrados.
O gate deve alinhar o workflow estável com contratos e capabilities executáveis; não basta preencher
um backend que continuaria falhando no primeiro encadeamento ou grant ausente.

## Contrato técnico congelado

1. Uma factory pública canônica construirá, para `new-feature`, configuração, provider router,
   tools confinadas, worktree externo, contexto, planning, executores, verification, approval,
   promotion, knowledge, evidence, cancellation e rollback usando somente componentes de produção.
2. `harness run new-feature` selecionará essa factory; workflows sem composição registrada
   continuarão falhando fechados, sem fallback genérico ou sucesso simulado.
3. A execução criará/recarregará o worktree pelo mesmo `execution_id`; escrita de agente, command e
   knowledge ficará confinada ao worktree, nunca ao checkout original antes da promoção aprovada.
4. Provider, credencial, trust, policy, grant, adapter ou aprovação ausente/incompatível falhará antes
   do efeito correspondente. Nenhum arquivo do projeto, marker ou resposta de modelo fabricará
   autoridade humana.
5. Resume e comandos subsequentes usarão artifact, configuração redigida, trust snapshot, identidades
   Git e worktree duráveis da mesma execução. Divergência bloqueará em vez de recompor silenciosamente.
6. Candidate, gates, approval vinculada ao conteúdo, promotion, knowledge transaction, evidence,
   cancel e rollback continuarão sob os serviços canônicos já promovidos; a F7.C1 fará wiring e as
   adaptações mínimas de fronteira, sem criar protocolos paralelos.
7. O E2E construirá e instalará a wheel em ambiente isolado, operará sobre repositório Git externo
   descartável e invocará CLI/factory pública. O modelo controlado usará um adapter HTTP de produção
   contra transporte local controlado; doubles permanecerão somente sob `tests/`.
8. Capabilities live que dependem de serviço, credencial ou Serena externo permanecerão opt-in e
   documentadas como limitações, sem registro simulado de produção.
