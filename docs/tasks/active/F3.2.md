## Contrato técnico congelado

1. A configuração efetiva terá seção `models` explícita: providers nomeados, adapter conhecido,
   modelo, base URL opcional, environment variable opcional para credencial, provider primário e
   fallbacks ordenados. Valores inválidos falham antes de qualquer chamada.
2. `ModelRouter.from_effective_config` lerá somente a configuração resolvida e a allowlist
   `data_egress.allowed_providers`; nenhum default oculto de CLI participará da rota.
3. O registry será instanciável e imutável por router. Só adapters implementados/explicitamente
   registrados poderão ser configurados; provider ausente, duplicado ou fora da allowlist falha fechado.
4. A rota inteira — primário e fallbacks — será validada quanto a registro e data egress antes de
   montar o prompt ou executar transporte. `AgentExecutor` chamará esse preflight antes da concatenação.
5. O router fará no máximo uma invocação por candidato. Retry do mesmo provider permanece no contrato
   F3.1; fallback só ocorrerá quando `ProviderError.retryable` for verdadeiro. Auth, invalid request,
   invalid response, cancelamento e not implemented interrompem sem tentar outro provider.
6. Provider/modelo devolvidos pelo servidor devem corresponder ao provider selecionado e a um modelo
   não vazio. O router nunca reescreve metadata com valores desejados/configurados.
7. Usage real `total_tokens` será registrado no `BudgetTracker` após cada resposta e o budget será
   verificado imediatamente antes de cada chamada/fallback. Budget excedido impede o próximo efeito.
8. `BudgetTracker` ganhará erro tipado, validação de contagens e consulta explícita de disponibilidade,
   preservando `PolicyEngine.record_usage` e falha fechada.
9. `NodeExecutionResult` poderá carregar `ModelCallMetadata` estrita derivada de `LLMResponse`.
   `GraphExecutor` persistirá provider, modelo, usage, request ID e response ID somente no outcome
   `NODE_COMPLETED`/`NODE_FAILED`, quando o provider real já é conhecido; `NODE_STARTED` não antecipará fato.
10. Resume/replay aceitará metadata ausente para nodes determinísticos e históricos, mas validará
    forma, tipos e consistência completa quando metadata de modelo estiver presente.
11. F3.2 não cria backend de agente padrão, não interpreta conteúdo do modelo como output do node e
    não executa tools. Backends explicitamente injetados continuam responsáveis por produzir o
    `NodeExecutionResult`; F3.3 implementará o loop de tool calls.
12. Nenhum segredo, prompt, conteúdo de resposta ou tool payload será persistido nos node events.

## Rollback

### Gatilhos

- rota/configuração inválida montar prompt ou causar transporte;
- provider fora da allowlist, não registrado ou duplicado ser executado;
- fallback ocorrer após auth, invalid request/response, cancelamento ou not implemented;
- budget não refletir `total_tokens` real ou permitir efeito depois de esgotado;
- node outcome omitir metadata de uma model call ou journal persistir segredo/conteúdo;
- replay aceitar metadata parcial, inválida ou adulterada;
- algum critério focado, regressão, qualidade, lock ou escopo falhar;
- implementação exigir arquivo, dependência, efeito ou critério fora do congelado.

### Procedimento não destrutivo

Parar e preservar saídas. Antes de commit de implementação, inverter somente hunks F3.2 com
`apply_patch`; depois de commit, usar `git revert` nos commits exclusivos da branch. Nunca usar reset
destrutivo, clean, descarte amplo, force-push ou sobrescrita de trabalho.

### Verificação pós-rollback

Confirmar `git status --short`, HEAD/checkpoint, `git diff --check` e zero diff de produto contra
`checkpoint/f3.2-ready`; repetir focais de routing/journal, suíte integral, mypy, Ruff, compileall e
`uv lock --check`.

## Evidências de execução

### Implementação observada

| Área | Resultado |
|---|---|
| Configuração efetiva | `ConfigResolver` inclui e valida providers, rota ordenada, allowlist de egress e teto de tokens antes de devolver a configuração |
| Registry | instância por router copia a configuração, aceita somente adapters conhecidos e cria OpenAI/local/Anthropic com modelo, URL, credencial por environment e política de retry configurados |
| Preflight | rota completa é validada antes de provider, composição do prompt ou transporte; candidato ausente, duplicado ou fora da allowlist falha fechado |
| Fallback | cada candidato recebe no máximo uma invocação do router; somente `ProviderError.retryable` avança; auth, invalid request/response, cancelamento e provider não implementado interrompem imediatamente |
| Identidade | provider/modelo reais de `LLMResponse` são preservados; divergência do provider selecionado gera `ModelRoutingIntegrityError` |
| Budget | `total_tokens` real alimenta `BudgetTracker`; esgotamento gera `BudgetExceededError` antes do próximo transporte |
| Journal | `ModelCallMetadata` estrita transporta provider/modelo/usage/request/response IDs; somente `NODE_COMPLETED`/`NODE_FAILED` recebe os campos, nunca prompt, conteúdo, segredo ou tool payload |
| Replay | metadata ausente continua compatível; conjunto parcial ou valores de tipo/forma inválidos são rejeitados antes de backend/mutação |
| Fronteira F3.3 | nenhum backend padrão, interpretação de conteúdo ou execução de tool foi adicionado |
