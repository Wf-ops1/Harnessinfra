## Problema comprovado

| Evidência reproduzível | Resultado observado |
|---|---|
| `rg -n "tool_loop_transcript" src/ai_engineering_harness/runtime/tool_loop.py` | a segunda rodada é outro prompt textual, sem `function_call_output`, `role=tool` ou `tool_call_id` nativos |
| inspeção de `BaseLLMProvider.call_tools` e `OpenAICompatibleHTTPProvider.call_tools` | contrato aceita somente `prompt: str`; não há continuação tipada ou reconstrução nativa de turnos |
| reprodução com `LLMResponse(prompt_tokens=100, completion_tokens=100, total_tokens=0)` e `BudgetTracker(max_tokens=1)` | resposta aceita; budget consome `0` e permanece disponível |
| reprodução de `_parse_tool_arguments('{"x":NaN}')` | parser aceita `{'x': nan}` embora não seja JSON interoperável |
| inspeção de `ToolLoopResult`, `ToolLoopError` e `NodeExecutionResult` | sucesso guarda somente o último `ModelCallMetadata`; erro guarda apenas tools; turnos anteriores se perdem |
| inspeção de `_append_node_event`/replay | outcome aceita somente um conjunto plano de campos `model_*`; não representa todos os calls do node |
| auditoria pós-merge da F3.3 | suíte anterior (`508 passed, 1 skipped`) não inspecionava o corpo HTTP da segunda rodada nem usage inconsistente |

Essas lacunas são anteriores a F3.4, mas afetam budget, auditabilidade, fallback e a capacidade dos
providers reais de continuar uma tool call. A correção é necessária antes de habilitar qualquer
ferramenta operacional com efeitos de arquivo, processo ou Git.

## Contrato técnico congelado

1. O primeiro model call continua usando `call_tools(prompt, schemas)`. Toda rodada posterior usará
   um contrato imutável e provider-neutral contendo prompt inicial, respostas normalizadas e resultados
   JSON-native ligados por `call_id`; nenhum transcript XML/textual será criado.
2. O provider Responses reconstruirá input nativo com mensagem inicial, itens `function_call` e
   `function_call_output`. O provider Chat Completions reconstruirá mensagens `assistant` com
   `tool_calls` e mensagens `role=tool` com `tool_call_id`. Schemas continuam presentes em cada rodada.
3. Fallback transitório pode reconstruir a mesma conversa em outro provider autorizado; prompt,
   resultados e IDs não serão persistidos pelo contrato de continuação nem convertidos em texto livre.
4. `LLMResponse` e `ModelCallMetadata` exigirão `total_tokens == prompt_tokens + completion_tokens`.
   Inconsistência falha como resposta inválida antes de budget, retorno ou próximo efeito.
5. Todo JSON vindo do provider será estrito: constantes não finitas e chaves duplicadas são rejeitadas
   em payload HTTP, structured output e argumentos de tool. Valores JSON-native não finitos também
   falham no contrato tipado.
6. Cancelamento será verificado pelo router antes de cada candidato, após uma falha transitória, após
   uma resposta e antes de fallback, cobrança ou retorno. Nenhuma continuação/fallback começa após o
   token ser cancelado.
7. `ToolLoopResult` preservará, em ordem, metadata de todos os model calls, mantendo acesso compatível
   ao último call e à contagem. `ToolLoopError` carregará calls já concluídos em qualquer falha posterior.
8. `NodeExecutionResult` terá uma sequência canônica de model calls. Helpers legados que recebem um
   único `model_call` continuarão aceitos, mas a representação interna e durável será a sequência.
9. O outcome do node persistirá `model_calls` como lista redigida de provider, modelo, usage e IDs.
   Replay validará ordem, tipos, usage e unicidade de response IDs; continuará aceitando somente o
   formato plano histórico de chamada única, nunca ambos no mesmo evento.
10. Nenhum prompt, conteúdo, argumentos/resultados brutos, header, token ou secret será adicionado ao
    journal. O contrato de conversa existe apenas em memória durante o loop.

## Rollback

### Gatilhos

- segundo request usar transcript textual ou omitir os vínculos nativos do provider;
- continuação perder call ID, resultado ou schema, ou fallback enviar contrato incompatível;
- usage inconsistente/non-finite/duplicado chegar ao budget ou JSON não estrito ser aceito;
- qualquer model call concluído desaparecer do sucesso, da falha ou do journal;
- replay novo quebrar eventos históricos válidos ou aceitar evento misto/adulterado;
- cancelamento permitir candidato, fallback, cobrança ou efeito posterior;
- prompt/conteúdo/payload bruto/secret aparecer no journal;
- gate focado, regressão, qualidade, package, documentação ou escopo falhar;
- solução exigir qualquer item proibido ou ampliar materialmente o congelado.

### Procedimento não destrutivo

Parar e preservar saídas. Antes de commit, inverter somente hunks F3.C1 com `apply_patch`. Depois de
commit, usar `git revert` nos commits exclusivos desta branch. Nunca usar reset/clean/force-push nem
descartar trabalho alheio. Se a descoberta exigir F3.C2 ou fase futura, registrar `BLOCKED` e
recongelar antes de qualquer edição adicional.

### Verificação pós-rollback

Confirmar status, HEAD/checkpoint, `git diff --check` e zero diff de produto contra
`checkpoint/f3.c1-ready`; repetir documentação, compatibilidade, suíte integral, quality e package.
